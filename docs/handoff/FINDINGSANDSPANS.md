# 1. Structured, and now

## The argument you didn't make, which is the strongest one

**There are already three error paths, and one of them solved this.**

```
IError                Reason (string)  +  Tokens (ReadOnlyMemory<Token>)
SymbolTable.Validate  IEnumerable<string>, interpolated English
runaway cascade       a thrown exception with a formatted Message
```

`IError.Tokens` **is a span**. The parse path already carries structure; the
rule path never got it, and the runtime path throws. So this is not adding a
mechanism — it is unifying three that exist, and inheriting the one that is
already right.

## The other reason: wording is design work, and tests are currently freezing it

We have revised message wording repeatedly — "bracket the call, not the
parameter", overflow-is-a-limit-not-a-mistake, "rename «smoothed», or respell
the pattern". Each revision is a wording change to a *rule* file, breaking
*rule* tests.

That is inertia pointed the wrong way. In a language whose error messages are
the teaching mechanism, wording has to stay cheap to improve. Welding it to the
rule guarantees it won't be.

## And the test rewrite is an improvement, not only a cost

45 message assertions today, several of the shape:

```csharp
Assert.Contains("glue", complaint);
```

That is mine, from `Resolutions.cs`, and it is a weak assertion — it passes for
the wrong reasons and would keep passing if the rule fired on the wrong symbol.
Structured findings make it exact: the kind, the offending name, the pattern
that made it glue. Better tests, not merely different ones.

## Shape

```
Finding
    Kind            discriminator — stable identity for tests AND for
                    IDE quick-fix dispatch
    Primary         Span
    Related         (Span, label)[]        ← the multi-span point
    Symbols         structured references, not interpolated strings
    Fixes           (Span, replacement)[]  ← optional; what makes a
                                             quick-fix possible at all
```

`Symbols` structured rather than interpolated matters for two consumers: the
renderer quotes consistently (« ») in one place, and the IDE makes them
clickable. Interpolation forecloses both.

## Two safeguards worth building with it

**Make the renderer total.** A test that enumerates the `Kind` enum and asserts
every value renders. Otherwise a new finding kind ships with no message and
nobody notices until a user hits it.

**Keep one golden-file test of rendered output across all kinds.** Then rule
tests assert structure and the golden test covers wording — so a wording change
shows up as a reviewable diff rather than as nothing at all. That is what
rustc's UI tests are for, and it is the piece that stops "wording is untested"
from becoming the new failure mode.

# 2. Spans — your design is right, with three refinements

Offset-and-length, origin optional, line/column on demand from a line-start
table. Correct. Three things it needs:

## Origin is required for identity, optional for display

Offsets are only comparable *within* a source. Two files both have an offset
42, and a diagnostic naming both is exactly the case we know is coming — the
module-composition conflict, where a pattern in module A collides with a name
in module B and **neither declaration is in the file being compiled**.

So split identity from display:

```
Span        { SourceId, Offset, Length }        SourceId always present
SourceText  { Id, Path?, Text, LineStarts }     Path optional
```

In tests the id is a synthetic buffer; in the Workbench it is the editor
buffer; in a build it maps to a path. Nothing needs a filename to be *correct*
— which was your requirement — but everything needs to know *which* text it is
an offset into.

The line-start table belongs on the `SourceText`, computed lazily on first
line/column request and cached. Never on the span.

## Zero length must be legal

"Expected a type after `=>`" points at a *position*, not a range. Length 0,
rendered as a caret rather than an underline. If the type forbids it, every
expected-X-here diagnostic has to fake a range and will point at the wrong
character.

## Injected symbols have no source text — and this is the case that crashes

`old smoothed` is generated by the compiler. It has no offset because it was
never written.

We already decided the diagnostic must never ask anyone to rename a generated
name; it names the declaration that caused the injection instead. That decision
has a representation consequence: **an injected symbol carries the span of its
origin**, and the message explains the indirection:

```
«old smoothed», injected by «let smoothed», collides with pattern glue
«smoothed» from «apply (_) smoothed (_)».
```

primary span → the `let smoothed` declaration
related      → the pattern that made it glue

Otherwise this is the first finding to need a null span, and null spans will
propagate into the renderer and the IDE as a special case in every consumer.

## One thing to state explicitly: units

`Token.Memory` is `ReadOnlyMemory<char>` and `RunningIndex` now advances by
`Memory.Length`, so offsets are **UTF-16 code units**. That happens to be what
LSP wants by default, so the IDE path is free. Worth writing down anyway, so
nothing later converts silently to bytes or codepoints — that class of bug is
invisible until someone puts an emoji in a string literal.
